## Decisions taken in this batch

### D1. Folder encryption streams straight into the cipher — no staging zip

`encrypt_to_qcx()` zipped a folder to a plaintext `.<out>.qc-staging-*.zip`
in the output directory, then encrypted that file, then deleted it. Three
costs, one of them a security cost:

- **Plaintext lands on the destination volume.** The output directory is
  often iCloud Drive, Dropbox or a USB stick. Sync clients upload new files
  within seconds and keep version history; a deleted staging zip can already
  be on someone else's server. On flash media, `os.remove` does not erase.
  README told users this. Telling them is not the same as not doing it.
- **2× disk.** The zip and the ciphertext coexist; a 40 GB folder needed
  80 GB free.
- **2× I/O.** Every byte was written, read back, then written again.

Fix: `zip_folder()` accepts a file-like sink, and a push-model
`ChunkEncryptor` turns the zip writer's `write()` calls into the same
`[seq][len][ct+tag]` chunk stream `stream_encrypt_payload()` produces (which
now drives the same sealer directly, copy-free). The "is this the last
chunk" question is answered the same way as before — a chunk is only sealed
once the *next* one has started — so the wire format, AAD and nonce schedule
are byte-for-byte the existing payload format. `zipfile` writes data
descriptors when the sink is unseekable, which is standard ZIP and what
every extractor (including ours) reads. No thread, no pipe: cancellation
and exceptions propagate on the calling thread. `tests/test_audit_2026_09.py`
watches the output directory during a folder encryption and asserts that
nothing but the 0600 ciphertext temp and the result ever appears.

Rejected: a pipe + zip thread (a thread boundary for error propagation and a
writer that can block forever on a full pipe when the reader dies); keeping
the staging file but in `/tmp` (moves the leak to the boot volume and breaks
the "same filesystem as output" size guarantee).

### D2. Adaptive compression inside the folder archive

`ZIP_DEFLATED` at zlib level 6 was applied to every member. On
already-compressed data (photos, video, archives, most office documents)
deflate gains nothing and ran at 40 MB/s, which made it the bottleneck of
folder encryption by a factor of eight. Each member is now sampled (first
64 KiB through zlib level 1); if that saves less than 5 % the member is
stored. Text keeps deflating at level 6.

### D3. Volume compaction triggers on dead space and record count

`save()` compacted when the journal exceeded 30 % of the baseline (and 8 MB).
Replay cost is per *record* (bodies are seeked over), so a large journal of
live writes was compacted for no reason, and dead space from deletes never
counted: a volume whose files were all deleted stayed full-size forever (no
"compact" action exists in either UI). The trigger is now dead bytes over
30 % of live bytes **and** over the 8 MB floor, or more than 10,000 journal
records. Design record updated in `volumes-delta-save.md`.

### D4. Tombstones a later write overwrites are dropped

The benchmark injected ENOSPC into a journal append and found data loss: the
editor atomic-save pattern emitted `[delete /final][write /final]`; the
tombstone was complete and durable, the write's body was not, and a fresh
open showed `/final` missing with `journal_suspicious=False`. Replay's write
sets the entry unconditionally, so the tombstone was redundant; the coalescer
now drops a `delete X` that a later `write X` or rename-onto-X in the same
batch materialises. The same failure now leaves the previous content in
place, and the in-session retry persists the new one (test reproduces both).

### D5. `compact()` writes through `mkstemp` and preserves the container's mode

`compact()` opened `<path>.tmp` with the process umask. A volume created 0600
came back 0644 after its first compaction, and a fixed temp name is a symlink
target. It now uses the same `mkstemp` pattern as creation and copies the
original's permission bits onto the replacement.

### D6. One `pread()` descriptor per container

Every blob read opened the container file: 44 µs of open/close against
2.5 µs of read, ~37 % of an LRU-miss FUSE read. The container now holds one
read descriptor for its life, reads with `os.pread` (position-free, so FUSE
workers share it without a lock), and drops it when a compaction replaces
the inode.

### D7. Bounded pre-authentication reads in `.qcv`

`_read_auth_params()` and `_read_encrypted_block()` trusted a uint32 length
before any authentication. Measured earlier as not a practical DoS (a short
file returns short), but a cap costs nothing: 1 MiB for auth params, 1 GiB
for the metadata and directory blocks (a million-entry index is ~250 MB).

### D8. `load_pkg()` validates field types

A crafted `.qcx` with `"version": "1"` or a string `threshold` raised
`TypeError` from a comparison, which `classify_error` reports as `internal`
and the Tk argv launch swallowed with a traceback (run-9 F-008). Every field
the decrypt path does arithmetic on is now type-checked at parse time and
reported as `format`; pathological JSON nesting is a format error too; the
argv launcher reports anything the parser raises.

### D9. `.qcx` format 2 / `.qcv` format 3: ML-KEM-768, recorded KDF parameters, full HMAC

`crypto.py` imported `kyber_py.kyber.Kyber768`, the round-3 CRYSTALS-Kyber
submission, while README's Security Overview said "NIST post-quantum
standard, FIPS 203". kyber-py 1.2.0 also ships `ML_KEM_768`, the FIPS 203
algorithm; the two differ in the Fujisaki–Okamoto transform and produce
different secrets for the same keys (verified). Because the KEM is defence in
depth over the password-derived key (README already explains why), this was
a labelling defect, not a key-exposure one — but "best it can be" means the
claim is true.

The new formats (`FORMAT_VERSION = 2`, `VOLUME_FORMAT_VERSION = 3`):

- name the KEM (`kem`: `"ML-KEM-768"`; absent means the legacy class, which
  is kept only to read old containers — the choice is a field, never a guess
  from the version number, and the field sits inside the HMAC);
- record the Argon2id parameters (`argon2`: `{t, m, p}`) so the shipped cost
  can be raised later without stranding every existing file — the gap the
  old `test_neither_format_records_its_kdf_parameters` documented; a reader
  is bounded to t ≤ 32, m ≤ 1 GiB, p ≤ 16 because a crafted file names them
  before anything is authenticated;
- HMAC every metadata field but the tag (review F-042: `mode`, `threshold`,
  `total`, `chunk_size`, `payload_offset` were outside it);
- drop the whole-plaintext SHA-256 from the `.qcx` envelope. Per-chunk GCM
  with the index and last-chunk flag as AAD plus the authenticated chunk count
  already prove every byte, its order and the length; the hash ran on
  in-memory plaintext (it never verified the disk write); it was 75 % of
  encryption time on this CPU; and `AESGCM.encrypt` does not release the GIL,
  so it could not be overlapped. A recorded hash in a format-1 file is still
  verified.
- `.qcv` `open()` compares every cleartext auth-params field with its sealed
  copy in the encrypted metadata (review F-044): an edited block is reported
  as tampering, not as a wrong password.

Compatibility: `tests/fixtures/v1/` holds real format-1 `.qcx` (password and
split-key) and format-2 `.qcv` containers written by the previous build with
the shipped Argon2 parameters, plus their credentials; `TestLegacyFixturesStillOpen`
opens every one of them on each run with the real KDF cost. A format-1
container is never rewritten as format 2; a version-2 volume keeps its version
through every compaction (the new fields are creation-time facts a rewrite
cannot add), so the previous release can still mount it. The Swift protocol
fixtures were regenerated (`format_version: 2`).

### D10. Release pipeline: nothing mutable, nothing debuggable, everything verifiable

- **`get-task-allow` on the shipping app (High).** `scripts/build.py --native`
  ran `xcodebuild … -configuration Release … build`; Xcode injects
  `com.apple.security.get-task-allow` into every non-archive build, and the
  DMG's `QuantaCrypt.app` carried it (verified on the artefact). With it any
  same-user process can take the hardened-runtime app's task port and read
  the memory holding passwords and shares — the very thing hardened runtime
  was enabled to prevent, and the same adversary the helper-locator work
  defends against. `CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO` is now passed,
  `build.py` asserts the entitlement is absent, and the release job asserts
  it again on the artefact it uploads.
- **Every action pinned to a commit SHA** with a version comment (Dependabot
  maintains both); a test fails on a tag pin.
- **XcodeGen by release + SHA-256** (`scripts/install_xcodegen.sh`) instead
  of `brew install`: it emits the build phases the signed xcodebuild executes.
- **Build backend from the lock** (`scripts/lock_subset.py setuptools`, then
  `--no-build-isolation` everywhere): `--require-hashes` pinned what is
  installed, not the setuptools that pip's build isolation fetched to build
  fusepy's sdist and the project itself. `pip install --upgrade pip` removed.
- **One interpreter for all three DMGs**: `PYTHON_VERSION` 3.13.15 for
  setup-python and the python.org universal2 pkg (its SHA-256 recorded); the
  x86_64 DMG had shipped 3.13.2 from February 2025.
- **`SHA256SUMS` and a Sigstore build-provenance attestation** attached to
  every release (`gh attestation verify <dmg> --owner alexboccard`), with the
  verification recipe in the release notes and README.
- **`persist-credentials: false`** on the bump-version checkout; the push
  authenticates explicitly.
- **Notarization groundwork**: with a real `CODESIGN_IDENTITY`, the
  executable and bundle get `--timestamp` and
  `scripts/hardened-runtime.entitlements` (library validation off for
  libfuse, unsigned executable memory for cffi); nested dylibs carry no
  entitlements.

### D11. Smaller core fixes

- `cli.py` reconfigures stdin to strict UTF-8 (review F-041, raised to Medium
  by the Swift auditor: the PyInstaller bootloader starts Python in isolated
  mode and never reads `PYTHONIOENCODING`, so the frozen helper's stdin
  followed the C locale and a non-ASCII password failed as "damaged file").
- `Service.emit` uses `allow_nan=False`: a NaN would be dropped by the Swift
  decoder and the request would hang forever.
- `mount_volume` refuses a non-empty mount point (review F-035).
- `FUSE_LIBRARY_PATH` from the environment is honoured only when it names a
  file under a FUSE backend location; fusepy hands it to `ctypes.CDLL` in the
  process that holds every mounted volume's key.
- `LRUCache.put` no longer evicts everything (itself included) for an entry
  larger than the cache.
- `_mark_quarantined` declares `argtypes` (it worked on arm64 only because
  libffi happened to sign-extend the `size_t`).
- Mnemonic decoding uses a dict (O(1), and no longer a linear scan whose
  duration depends on the secret word); `mnemonic_to_share` rejects index 0
  and values at or above the modulus, as `decode_share` always did.
- `_chunk_nonce` uses integer XOR instead of a Python generator.

## 2026-09-05 addendum — two defects the local rebuild exposed

- **`dist/` name collision.** The Tk product `dist/quantacrypt.app` and the
  native `dist/QuantaCrypt.app` are the same path on a case-insensitive APFS
  volume; building both in sequence made PyInstaller's "Removing dir
  dist/quantacrypt.app" delete the native app (its DMG had already been
  written, so the shipped artefacts were unaffected; CI builds each product
  on its own runner and never hit it). The Tk app now lands in
  `dist/tk/quantacrypt.app`; DMGs stay in `dist/`. Workflow verify paths, the
  release-script test, README and RELEASING follow.
- **Drag-and-drop silently dead in the Tk app on Python 3.13+.**
  `tkinterdnd2-universal` 1.7.3 does `from tkinter import tix` at import;
  `tkinter.tix` was removed in 3.13, so the import fails, `build.py` prints a
  warning and bundles nothing, and the launcher falls back to a plain `Tk()`
  — every Tk DMG built on 3.13 shipped without drop support and nothing in
  the suite noticed (tests mock the module). The `dnd` extra now names the
  maintained `tkinterdnd2` (0.6.3: same import name and `TkinterDnD.Tk`
